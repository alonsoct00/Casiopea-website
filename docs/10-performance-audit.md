# 10 — Performance Audit

## What's already implemented (good baseline to preserve)

- **Custom IntersectionObserver lazy loading** for both images and videos, hand-written in `javascripts/functions.js:247-358` — no external lazy-load library dependency. Images use `data-src`(+`data-srcset` for `<picture>` sources); videos use `data-src` on `<source>` tags, `.load()` triggered on intersection. Includes a synchronous fallback for browsers without `IntersectionObserver` support (loads everything immediately rather than leaving broken images).
- **WebP adoption**: 140 `.webp` files exist across the site, generally paired with `<picture>`/`<source type="image/webp">` fallback — see `OPTIMIZATION-GUIDE.md` for the documented `cwebp` conversion workflow used to produce them.
- **Minified vendor libraries**: jQuery, Bootstrap CSS/JS, Font Awesome CSS, Isotope, Waypoints all ship as `.min` files.
- **Responsive video hero**: `index.html` chooses a differently-sized video source (desktop vs. mobile) via a viewport-width check before injecting `<source>` tags, avoiding downloading a large desktop video on mobile.
- **CSS custom to the site is separated** from Bootstrap (`the-casiopea-styles.css`), so Bootstrap itself is never modified — good for cache stability across deploys.

## Gaps / inconsistencies found

| Issue | Detail |
|---|---|
| `functions.js` itself is not minified | 358 lines / ~11.6 KB uncompressed, loaded on every page, contains both the Web Components and all site behavior including the lazy-load engine. Not a huge win, but inconsistent with the "minify everything else" pattern already in place. |
| `style.css` vs `style.min.css` split | Root pages (6) load `style.min.css`; all 22 project pages + faq.html load the **unminified** `style.css`. This means the majority of page loads (23 of 29) are pulling the larger, unminified stylesheet. Worth flagging — but changing which file is linked on 23 pages is a real, if small, risk to visual output and is outside the stated scope of "add i18n"; recommend surfacing to the user as a separate follow-up rather than bundling into this project. |
| `.mov` fallbacks still shipped everywhere | Every video that has an `.mp4` also ships a `.mov` sibling as a `<source>` fallback. `.mov` is rarely needed by any current browser and roughly doubles the video payload per hero/gallery clip if a browser ever *does* pick it (in practice modern browsers all pick `.mp4` first, so the extra `.mov` file mostly just adds dead weight to the deploy, not to any single page load — since only the chosen `<source>` downloads). Low priority. |
| Some images lack a true raster fallback | At least one confirmed instance (`dos-camaleones.html:131-132`) where both the `<source type="image/webp">` and the `<img>` fallback point at the same `.webp` file — meaning browsers without WebP support get nothing. Rare edge case in 2026 but worth noting since Phase 12 explicitly asks to preserve image optimization behavior; this existing gap should not be "fixed silently" as a side effect of unrelated i18n edits (could subtly change rendering) — flag only. |
| Google Fonts loaded via blocking `<link>` | Two separate `<link>` calls to `fonts.googleapis.com` on every page (Roboto, Inconsolata), not preconnected/preloaded, not self-hosted. Pre-existing, not part of this project's scope. |
| No CDN/versioning on local static assets | No cache-busting query strings or hashed filenames on CSS/JS — a deploy overwrite could serve stale cached CSS/JS to returning visitors. Pre-existing, unrelated to i18n; flagging only for completeness of the audit. |

## Direct implications for the i18n implementation (Phases 6/7/12)

1. **Translation JSON files must be small and cached client-side after first load** (per Phase 12's explicit requirement) — given the site has no existing fetch-based data loading pattern at all (everything is currently inline HTML), the content-loader introduced in Phase 7 will be the first network-based data fetch on the site. It should use the browser cache (`fetch` with default caching, or an in-memory module-level cache keyed by locale) and must not re-fetch on every page navigation given this is a traditional multi-page site (full page loads between pages, not an SPA) — each page navigation is a fresh JS context, so "cache loaded JSON" most realistically means relying on standard HTTP caching (`Cache-Control` headers on the JSON files) rather than an in-memory cache that would need to survive a full page reload it can't survive.
2. Because this is a fully static multi-page site (no client-side router), the `i18n.js`/`content-loader.js` scripts will need to run on **every** page load, reading `localStorage` and re-fetching/re-rendering translated text before paint to avoid FOUC (Phase 6's explicit requirement) — this is a meaningfully different performance profile than a typical SPA i18n setup and should be designed for from the start (Phase 4 architecture) rather than adapted later.
3. Lazy-loading of images/videos must not be disturbed by the content loader — if project galleries move into JSON-driven rendering (Phase 7), the rendered `<picture>`/`<video>` markup must still carry `data-src`/`loading="lazy"` exactly as today, meaning the content loader needs to emit markup, not just text, for anything that currently uses the lazy-load attributes.
